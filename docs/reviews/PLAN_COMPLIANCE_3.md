- **فهارس مركَّبة جديدة (سبرنت 6.6.3)**: `(tenant, legal_entity, date)`

## 3. نتائج الأداء — سداد دَين 6.6.3 (§6.4، سبرنت 6.6.7)

**على `perf-baseline` (مستأجر أداء مخصَّص، `manage.py seed_perf
--lines 100000` — 100,016 سطر قيد حقيقي عبر Postgres حقيقي):**

| الاستعلام | قبل (حلقة Python / N+1) | بعد (SQL واحد عبر ORM) | الهدف |
|---|---|---|---|
| `trial_balance()` | 0.640s | 0.208s | — (لم يكن ديْنًا) |
| `balance_sheet()` | 0.858s | 0.157s | — (لم يكن ديْنًا) |
| `ledger_lines()` (حساب واحد، سنة كاملة) | **4.970s** | **1.403s** | < 2.000s ✅ |
| `period_checklist()` | **6.206s** | **0.235s** | < 2.000s ✅ |

**التفاصيل التقنية:**
- `ledger_lines()`: الرصيد الجاري كان يُراكَم بحلقة `for line in
  queryset: running += ...` في Python — أصبح الآن `Window(expression=
  Sum(...), order_by=...)` عبر Django ORM (دالة نافذة SQL واحدة،
  Postgres نفسه يحسب التراكم)، مع `.values(...)` بدل تجسيد موديلات
  كاملة لتخفيف حمل الكائنات على 50 ألف سطر.
- `period_checklist()`: البطء الحقيقي كان في
  `_posted_documents_without_attachment` — استعلام `.exists()` **منفصل
  لكل مستند مرحَّل في الفترة** (≈5,177 قيد يدوي وحده على `perf-baseline`)
  — دَين غير مذكور بالاسم في نص السبرنت نفسه (الذي يذكر `ledger_lines`/
  `period_checklist` عامة) لكنه اكتُشف بالتنميط المباشر (profiling)
  لكل فحص فرعي على حدة، وكان يمثّل 6.264 من إجمالي 6.206 ثانية — أُصلح
  ببادلة استعلام واحد لكل نوع مستند (`object_id__in=[...]`) ثم طرح
  Python بسيط على القوائم (set difference) بدل استعلام قاعدة بيانات
  لكل عنصر.
- كل الاستعلامات الجديدة عبر ORM Django البحت (`Window`/`F`/`Sum`/
  `values_list(...__in=...)`) — لا `cursor.execute()` خام يتجاوز
  `cps.tenant_id` في أي مكان.

**الشاشات المستهلكة (دفتر الأستاذ، كشف الطرف، حركات الخزينة، قائمة
الإقفال) أعيد اختبارها بأرقام ثابتة قبل/بعد** في
`backend/tests/test_entity_subtree_scoping.py` — مستأجر بفرعين، تقرير
الشركة = مجموع الفرعين + مستنداتها المباشرة، على مستوى الخدمة ومستوى
واجهة API معًا؛ 663/663 اختبارًا على Postgres حقيقي يمر بعد التغيير
(660 + 3 جديدة).

## 4. تأكيد تشغيلي — بادلة النسخ الاحتياطي التلقائية (6.6.4)

**لم تُختبَر بعد من الصفر على صورة مُعاد بناؤها فعليًا بلا تدخّل يدوي
مسبق.** السجل الفعلي (`docs/ops/backups.log`، 2026-10-01):
أول تشغيلة حقيقية لـ`backup.sh` بعد بناء `upload_backup_to_s3.py`
كشفت أن البادلة (`cps-backups-interim`) غائبة (`NoSuchBucket`) —
أُنشئت **يدويًا** للتحقق الفوري من مسار الرفع نفسه (نجح)، وكود
الإنشاء التلقائي (`CPS_UPLOAD_ENSURE_BUCKET=1`) لم يُعَد اختباره منذ
ذلك الحين إلا عبر مساره الآمن idempotent (البادلة موجودة فعلًا →
`BucketAlreadyOwnedByYou` → نجاح بلا إنشاء حقيقي) على كل نشر تالٍ
(6.6.5، 6.6.6، 6.6.7). **لإغلاق هذا البند فعليًا:** حذف البادلة الآن
(بيانات مكرَّرة على نفس الخادم، ليست حماية off-site حقيقية حسب تصميم
6.6.4 نفسه) وتشغيل `backup.sh` مرة أخرى على الصورة الحالية المُعاد
بناؤها عدة مرات منذ ذلك — لم يُنفَّذ بعد لأنه يمس بنية تخزين الحي
مباشرة بلا إذن صريح؛ يُنفَّذ إن طلب المالك ذلك تحديدًا.
