## 3. e2e spec 10 (reset-password)

Why it never ran: nothing referenced it. Added in 7.2.9 (44253ac), never put
in e2e.sh, and e2e.sh is the only runner CI reaches
(ci.yml `make e2e` -> scripts/e2e.sh).

It could not have run as written anyway. It opens `fatma.<host of BASE_URL>`,
and BASE_URL is a bare IP both here and in CI:

    Error: page.goto: Protocol error (Page.navigate): Cannot navigate to invalid URL

Fix: e2e.sh phase 10 runs it against `http://localhost:<same port>`.
Chromium resolves `*.localhost` to loopback (RFC 6761).

What it does when it runs:
- It loads /reset-password on a tenant host.
- It asserts the manual subdomain field is hidden.
- It submits, and asserts that the confirm request body carries
  subdomain=fatma and the token.
- The confirm endpoint is faked inside the spec with page.route(). No request
  reaches any backend or tenant (nothing reaches fatma on dev, and nothing
  touches live).

Result: PASSES (1 passed, 2.9s). It also passes in the full e2e.sh run
(below).

On live's dummy.EmailBackend: the spec cannot assert anything about that.
It never requests a reset email and never reads one. It tests only the
frontend half: the host's subdomain reaching the confirm call. That live
sends no reset email (the declared exception) is untested by this spec and by
any other e2e spec.

The first commit attempt was refused by scripts/precommit_guard.sh (rule 50):

    !!! COMMIT REFUSED by scripts/precommit_guard.sh (rule 50) — 2 finding(s):
      frontend/package-lock.json:33: credential with a literal value
      frontend/package-lock.json:4548: credential with a literal value

Both lines are the npm package js-tokens, a dependency of the ESLint
packages, mapped to a version range (^4.0.0, and ^3.0.0 || ^4.0.0). The
guard's key pattern reads "tokens" as a token with a quoted literal.

I did not bypass the hook. I made one narrow exemption: a JSON line whose
whole value is a version range (digits and dots, optional ^ or ~, `||`
alternatives) is not checked as a credential. Nothing else changed.

The guard's credential half had no test until now; only the exclusion list
was tested. backend/tests/test_precommit_guard.py adds 9 cases. 3 must pass:
version-range dependency lines. 6 must be refused:
- api_token with a hex value;
- token with a value that starts like a version;
- a version-like prefix with a non-version suffix;
- a version range plus a password on the same line;
- a password assignment;
- an env-style PASSWORD=.
