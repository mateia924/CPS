Verdict: the counts are at parity, but the parity work is PARTIAL. Every test

settings. The same count does not mean the same code paths. Remaining
differences:

1. Attachment storage. CI: `ATTACHMENT_STORAGE_BACKEND=local` (filesystem).

2. Virus scanning. CI: `ATTACHMENT_SCAN_ENABLED=false`. Local: true, against
   dev ClamAV (CLAMD_HOST=clamav).
3. Environment. scripts/pytest_run.sh copies cps-dev-backend-1's entire
   environment into the test container. That is 45 variables CI does not set,
   including real secrets: backup cloud keys, the backup encryption
   passphrase, the SMTP password, MinIO keys and the link-signing key. Tests
   could pass locally because of a variable CI lacks. Every secret is also
   readable by any test process.
4. CPS_ENVIRONMENT: `dev` locally, `ci` in CI. Code that branches on it runs
   differently.
5. Platform database. Locally PLATFORM_DATABASE_URL is its own value. In CI it
   is unset, so it falls back to DATABASE_URL, the same database. The
   `platform` alias is set up differently.
6. Database server. Locally: dev's long-lived Postgres 16.15, shared with the
   dev app. In CI: a fresh `postgres:16-alpine` service, floating patch
   version.
7. Redis. Locally: dev's Redis 7.4.11, shared with the dev app. In CI: a fresh
   `redis:7-alpine`, floating patch version.
8. Python and OS. Locally: python:3.12-slim (3.12.15, Debian libs, libmagic).
   In CI: setup-python 3.12.x on Ubuntu 24.04 with Ubuntu's libmagic1.
   Dependencies are the same: every line in requirements*.txt is pinned.
9. Invocation. CI runs four separate pytest processes from backend/tests, with
   --create-db on the first only. The standard local runner
   (scripts/pytest_run.sh) runs one process from backend/. Order, test-DB
   lifecycle and node ids differ. The four-group runner used for the table

## 4. cp -i hangs

No repo script did it. Non-interactive bash does not expand aliases, and
cron calls the scripts directly. The source is /root/.bashrc lines 5-7.
Claude Code's Bash tool snapshots root's profile, so the agent's shell had
`alias -- cp='cp -i'` (snapshot line 71) with a non-terminal stdin. Both
hangs were agent commands.

Fix: the three aliases are defined only when stdin is a terminal. The exact
before/after, the proof, the reason and how to revert are recorded in
docs/ops/DEPLOY.md, "Host change: root's `-i` aliases apply on a terminal
only, 2026-10-20".

Proof that the human path still prompts. An interactive root shell on a
pseudo-terminal:

    [root@cps cps]# rm /tmp/tmp.Ptdo6GbiWU/victim.txt
    rm: remove regular file '/tmp/tmp.Ptdo6GbiWU/victim.txt'? n
    file still there after answering n: yes

With no terminal, `rm` runs without a prompt (rm-exit=0).

The current session's shell snapshot predates the fix, so agent commands
here keep writing `command cp -f`. New sessions do not get the aliases.

## 5. The aging race: demonstrated, real defect

Setup:
- A fresh smoke-* tenant (scripts/e2e_access.sh) and a real browser, against
  the unmodified dev frontend and backend.
- The demonstration spec existed only in a copy of the tree. It is kept at
  the scratchpad path 98-aging-race-demo.spec.ts and was never committed.
- The aging API responses were real. Only `total` was replaced by a marker so
  the two responses can be told apart: receivable = 1111.11,
  payable = 2222.22. The receivable response was held back 4 s.

Steps:
1. Side "receivable", Submit. Request A is slow.
2. 0.3 s later: side "payable", Submit. Request B is fast.

Output:

    RACE response arrival order: payable then receivable
    RACE 1.5 s after B, total line: الإجمالي: 2,222.22
    RACE final: side select shows "payable"; total line: الإجمالي: 1,111.11

Screenshots: docs/uat/screens/8.2.1-race/1-after-fast-payable.png (correct),
2-after-slow-receivable.png (wrong).

In the final screenshot:
- the side filter reads «الذمم الدائنة (الموردون)» (payable), and the detail
  column reads «المورد» (supplier);
- the total is the receivable figure, 1,111.11;
- the heading «حسب العميل» (by customer) contradicts the filter.

The wrong numbers sit under the right filter.

Cause: `load()` in src/app/dashboard/reports/aging/page.tsx writes whatever
response arrives last. Nothing cancels the earlier request or ignores its
response.

Not demonstrated, so not claimed: whether the other money screens share it.
Their loads have the same shape (payables-by-week, statement, ledger,
trial-balance, balance-sheet, income-statement). One demonstration each
would settle it.

This changes the premise of deferring the lint backlog. The decision is the
owner's.
