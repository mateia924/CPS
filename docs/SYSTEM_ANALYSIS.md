## 1. الرؤية ونطاق المنتج

CPS منصة SaaS متعددة المستأجرين لإدارة الأعمال، تبدأ كنظام **محاسبي ومخزني** كامل لسوق سعودي/خليجي أولًا مع بنية عالمية (لغات، عملات، أنظمة ضريبية قابلة للتوصيل).

**الفلسفة الحاكمة:** العميل الصغير (فواتير خدمية فقط) هو الأغلبية المتوقعة من العملاء، فالنظام يُصمَّم له أولًا، والقدرات الكبيرة (قابضة، شقيقة، مخزون متعدد المستودعات) "تُفتح" فوقه دون ترحيل بيانات. ERP كامل يظهر كبرنامج فواتير بسيط حتى يحتاج العميل أكثر.

**النطاق الأول المعتمد (بترتيب التنفيذ):** الهيكل التنظيمي والصلاحيات → إدارة المنصة → البيانات الرئيسية → الدليل المحاسبي → السندات → الفترات والأرصدة الافتتاحية → الأصناف والمستودعات → المشتريات → الفوترة والفوترة الإلكترونية السعودية → التقارير → التقارير المجمّعة.

**خارج النطاق الحالي (مؤجل):** الموارد البشرية الكاملة، نقاط البيع Offline، التصنيع، دورة العمل. البنية تسمح بإضافتها لاحقًا كوحدات.

## 2. حالة المشروع الحالية

ما تم إنجازه فعليًا وتم اختباره على Postgres حقيقي داخل Docker على سيرفر التطوير (Oracle Linux، مسار `/opt/cps`، منفذ 3000):

- Backend: Django 5.2 LTS + DRF + SimpleJWT، تعدد مستأجرين بعزل صريح على مستوى الصف.
- تسجيل شركة (Tenant + Owner + دليل حسابات أولي في transaction واحدة)، تسجيل دخول بـ subdomain + email + password.
- عملاء، منتجات، فواتير متعددة البنود بحساب خادمي كامل للإجماليات، وترحيل قيد متوازن عند الاعتماد.
- Frontend: Next.js + TypeScript، عربي RTL افتراضي مع تبديل للإنجليزية.
- Infra: docker-compose (postgres, redis, backend, celery_worker, frontend, nginx) بكل volumes معلّمة `:Z` لـ SELinux.
- ثغرة أمنية حرجة اكتُشفت وأُصلحت: `ModelBackend` كان يسمح بتجاوز عزل المستأجر عند الدخول. الدرس: **اختبارات عزل المستأجر إلزامية في كل سبرنت.**
- **سبرنت 0 (التحصين):** 18 اختبار pytest ضد Postgres حقيقي، حاويات backend/celery_worker non-root (gosu privilege drop)، CI فعّال (ruff + pytest + Postgres service)، Makefile.
- **سبرنت 1 (الهيكل التنظيمي + الصلاحيات + الوضع المبسّط):** app `organization` (LegalEntity شجرة قانونية عمق غير محدود + CostCenter شجرة تحليلية)، app `access` (Permission كتالوج ثابت، Role تعديل لكل مستأجر، UserEntityAccess)، `Invoice`/`JournalEntry` يحملان `legal_entity` إلزامي، `InvoiceLine`/`JournalLine` يحملان `cost_center` اختياري على مستوى السطر، `TenantFeatures` + `simplified_mode` في `/api/auth/me/`. تسجيل شركة جديدة الآن يُنشئ COMPANY+BRANCH افتراضيين + الأدوار الأربعة تلقائيًا. بيانات ما قبل هذا السبرنت هوجرت بـ data migrations (موثّقة في القسم 11). 36 اختبار pytest إجمالًا. تفاصيل كاملة في README.

**التقدير الواقعي:** ما أُنجز ≈ 12-15% من ERP بالنطاق أعلاه (بعد سبرنت 1). هيكل تنظيمي وصلاحيات حقيقيان الآن فوق الأساس التجاري، لكن Master Data الموحّد والدليل الشجري الكامل والسندات والفترات المالية لم تُبنَ بعد.

## 3. القرارات المعمارية الجوهرية

### 3.1 الهيكل التنظيمي: شجرتان مستقلتان

**القرار:** فصل تام بين الهيكل القانوني والهيكل التحليلي. لا تُدمج "الإدارة" كمستوى في الشجرة القانونية.

| | الشجرة القانونية | شجرة مراكز التكلفة |
|---|---|---|
| المستويات | قابضة ← شركة شقيقة ← فرع (عمق غير محدود عبر parent) | إدارة / سيارة / مستودع / موظف / مشروع (عمق غير محدود) |
| طبيعته | كيان بذمة مالية ورقم ضريبي وميزانية مستقلة | تصنيف "لصالح مين" للإيراد والمصروف |
| يصدر مستندات؟ | نعم | لا |
| له ميزانية؟ | نعم | لا — قائمة دخل وكشف تفصيلي فقط |

**المبرر:** الإدارة تخدم كل الفروع ولا تنتمي لفرع واحد؛ القيد الواحد قد يتوزع على عدة إدارات؛ إعادة الهيكلة الإدارية يجب ألا تلمس البيانات القانونية أو الضريبية؛ التقرير المجمّع للقابضة يعمل على الشجرة القانونية فقط.

**الفرع والشركة يتصرفان كمراكز تكلفة تلقائيًا** في التقارير لأن كل سطر يحمل الكيان القانوني — لا يُكرَّران يدويًا كمراكز تكلفة.

### 3.2 مركز التكلفة = مركز ربحية على مستوى السطر

- شاشة مراكز التكلفة: كود، اسم، **نوع** (سيارة/مستودع/موظف/مشروع/إدارة/عام)، أب اختياري، **ربط اختياري بكيان موجود** (موظف من Master Data، مستودع من المخزون) تطبيقًا لمبدأ "التسجيل مرة واحدة"، حالة.
- **لا يوجد نوع "حساب محاسبي"** لمركز التكلفة: الحساب هو البُعد الثاني المستقل (نوع المصروف)، ومركز التكلفة هو البُعد الأول (لصالح مين). تقرير مركز التكلفة يعرض التفصيل حسب الحساب تلقائيًا.
- **قاعدة ثابتة:** حقل مركز التكلفة **على مستوى السطر** (لا المستند) في كل مستند: فواتير بيع وشراء، السندات الثلاثة، القيود اليدوية — للإيرادات والمصروفات معًا. سند صرف واحد يمكن توزيعه على عدة مراكز بعدة أسطر.

### 3.3 البيانات الرئيسية: "تسجيل مرة واحدة" (Master Data)

كيان موحد **Party (طرف)** يحمل **أدوارًا**: عميل / مورد / موظف / شركة شقيقة / بنك. الجهة الواحدة قد تكون عميلًا ومورّدًا معًا دون تكرار. كل Party يُربط تلقائيًا بحساب جاري في الدليل عند إنشائه.

شاشات التسجيل المطلوبة: الأطراف بأدوارها، البنوك، الصناديق، العُهد، الأصول (تسجيل فقط في هذه المرحلة)، المستودعات.

### 3.4 الدليل المحاسبي الشجري

- هرمي متعدد المستويات، عمق غير محدود، يصلح لكل الأنشطة والقابضة.
- حسابات جاري تلقائية للأطراف، وحسابات بينية للشركات الشقيقة (علامة `is_intercompany` على القيود لتمكين الاستبعاد لاحقًا).
- **قوالب دليل حسب النشاط** (خدمي مبسّط ~15 حسابًا / تجاري / صناعي / قابضة) تُطبَّق عند التسجيل بدل دليل واحد للجميع.

### 3.5 المستودعات

| الحقل | القرار |
|---|---|
| الفرع | إلزامي — المستودع تابع لكيان قانوني واحد |
| حساب المخزون / تكلفة البضاعة المباعة / فروق الجرد | ثلاثة حسابات من الدليل، تُحرَّك تلقائيًا |
| مركز تكلفة مرتبط | اختياري |
| مستودع افتراضي للفرع | نعم/لا |

**قاعدة الظهور:** نوع الصنف (مخزني/خدمي) هو ما يحدد طلب المستودع، **على مستوى السطر** لا الفاتورة: صنف مخزني → مستودع إلزامي (افتراضي الفرع تلقائيًا)؛ صنف خدمي → الحقل مخفي تمامًا ولا حركة مخزون. إذا لم يوجد إلا مستودع واحد نشط للفرع يُخفى الحقل. النتيجة: العميل الخدمي لا يرى كلمة "مستودع" أبدًا، والفاتورة المختلطة (جهاز + تركيب) تعمل صحيحًا.

### 3.6 تقييم المخزون

**متوسط مرجّح متحرك** (Moving Weighted Average) — قرار نهائي. التصميم يسمح بإضافة FIFO لاحقًا كخيار على مستوى المستأجر دون إعادة بناء.

### 3.7 المشتريات: مسارين على محرك واحد

- **الدورة الثلاثية:** طلب شراء → استلام → فاتورة مورد (للشركات ذات قسم مشتريات).
- **الفاتورة المباشرة على مرحلة واحدة:** تولّد داخليًا نفس الحركات (طلب + استلام + فاتورة) — محرك واحد لا كود مكرر.
- **أنواع البنود في فاتورة المورد:** صنف مخزني (يدخل المخزون ويُكلَّف) / خدمة / مصروف لحساب محدد (يذهب للمصروف مباشرة). لكل بند نسبة ضريبة ونوعها (قابلة للخصم / غير قابلة).
- **سند الصرف اختياري عند الحفظ:** "دفع نقدي الآن" (سند تلقائي من صندوق/بنك مختار) أو "على الحساب" (يُقيَّد على جاري المورد).

### 3.8 السندات (قبض / صرف / تسوية)

- متعددة الأسطر، كل سطر بحساب + مركز تكلفة + كيان قانوني.
- **بند مصروف بضريبة مباشرة** في سند الصرف دون الحاجة لمورد مسجّل (مثال: فاتورة بنزين) — يمنع إنشاء موردين وهميين لكل مصروف صغير.
- الربط بالبنوك والصناديق والعُهد وتوليد القيود تلقائيًا.

### 3.9 الفترات المالية المرنة

- **سنة مالية** تبدأ من أي تاريخ (ميلادي أو هجري).
- **فترات** داخلها بأي عدد وأي طول يحددها العميل.
- **ضابط غير قابل للتنازل:** الفترات داخل السنة **متتالية بلا فجوة وبلا تداخل** — يتحقق النظام تلقائيًا.
- حالة كل فترة: **مفتوحة / مقفلة / مقفلة نهائيًا** (المقفلة يفتحها مدير الحسابات؛ النهائية لا تُفتح بعد اعتماد الميزانية).
- كل مستند يتحقق أن تاريخه في فترة مفتوحة قبل الحفظ. نفس الآلية تقفل الفترة الافتتاحية.

### 3.10 الأرصدة الافتتاحية

شاشات لأرصدة الحسابات والأطراف والمخزون، بشرط: **قيد الافتتاح متوازن إلزاميًا**، مخزون الافتتاح مقيَّم بالمتوسط المرجّح، أرصدة الفروع متوازنة، ثم **قفل الفترة الافتتاحية** لمنع تغير الأرقام.

### 3.11 العملات والضرائب والدول

- كل مبلغ يُخزَّن بالعملة الأصلية + سعر الصرف وقت المعاملة (قرار من الدراسة الأولى).
- تقرير العملات يشمل الأرصدة بالعملة الأجنبية و**قيد فروق إعادة التقييم** في نهاية الفترة.
- إقرار الضريبة (مخرجات − مدخلات) يُشتق مباشرة من بنود الفواتير.
- كل شركة/فرع/طرف يحمل رمز دولة → تقارير حسب الدولة كفلتر.
- **الامتثال الضريبي كحزمة قابلة للتوصيل لكل دولة** (ZATCA أولًا).

### 3.12 الفوترة الإلكترونية السعودية (ZATCA)

- **المرحلة 1:** توليد QR وXML بمعيار الهيئة — داخل سبرنت الفوترة.
- **المرحلة 2:** ربط فعلي مع بوابة الهيئة، توقيع رقمي، Clearance — تحتاج **شهادة تشفير من الهيئة وبيئة Sandbox**، وهي إجراء إداري خارج قدرة Claude Code.
- **إجراء فوري مطلوب من الإدارة:** بدء التسجيل مع ZATCA والحصول على بيئة الاختبار **بالتوازي من الآن**، لا عند الوصول للسبرنت.

### 3.13 العميل الصغير: وحدات مفعّلة ووضع مبسّط

- جدول **الوحدات المفعّلة لكل مستأجر** (Tenant Feature Flags) تتحكم به الباقة.
- **الوضع المبسّط:** إذا كانت شركة واحدة/فرع واحد، يُخفى الهيكل التنظيمي تمامًا (لا "قابضة" ولا "شقيقة")، وقائمة العميل الخدمي: عملاء — فواتير — سندات قبض — تقارير.
- المحاسبة تعمل في الخلفية دون أن يراها؛ تفعيل وحدة لاحقًا لا يتطلب ترحيل بيانات.
- **قاعدة تصميم لكل شاشة:** الحقول الأساسية ظاهرة، والمتقدم مطوي.

### 3.14 إدارة المنصة (Super Admin)

نظام منفصل تمامًا عن إدارة الشركة:

| العنصر | القرار |
|---|---|
| المستخدمون | **جدول منفصل** عن مستخدمي المستأجرين + 2FA إلزامي |
| المسار | `/platform/` أو نطاق فرعي مستقل |
| الشاشات الأساسية (سبرنت 2) | لوحة المستأجرين (حالة، باقة، نشاط، تعليق/تفعيل)، الباقات والحدود (وحدات مفعّلة + حدود مستخدمين/فروع/فواتير/تخزين)، سجل تدقيق غير قابل للتعديل |
| الشاشات اللاحقة (بعد سبرنت 10) | الاشتراكات والفوترة الخاصة بالمنصة (تذكير → سماح → تعليق للقراءة فقط → أرشفة، **لا حذف تلقائي أبدًا**)، الانتحال للدعم (بإذن، علامة واضحة، وقت محدد، تدقيق كامل)، المراقبة التشغيلية، Feature Flags، إعدادات عامة، متابعة فشل إرسال الفوترة الإلكترونية عبر كل العملاء، تصدير بيانات العميل الكامل |

## 4. القواعد الثابتة الملزمة في كل سبرنت

هذه القواعد تُضمَّن حرفيًا في كل prompt لـ Claude Code:

1. **عزل المستأجر:** كل استعلام مقيّد صراحة بـ `request.user.tenant`؛ لا مسار API يقبل `tenant_id` من العميل؛ الوصول لسجل مستأجر آخر يُرجع 404 لا 403.
2. **المبالغ المالية تُحسب خادميًا فقط:** لا حقل إجمالي/ضريبة يُقبل كمدخل.
3. **كل سطر معاملة يحمل:** `legal_entity` (إلزامي) + `cost_center` (اختياري) + العملة وسعر الصرف.
4. **كل قيد محاسبي متوازن إلزاميًا** ولا يُحفظ غير المتوازن.
5. **كل مستند يتحقق من فترة مالية مفتوحة** قبل الحفظ (من سبرنت 6 فصاعدًا).
6. **المستودع على مستوى السطر** ويظهر فقط للأصناف المخزنية (من سبرنت 7).
7. **الحقول الأساسية ظاهرة والمتقدم مطوي** في كل شاشة.
8. **اختبارات pytest لكل سبرنت** تشمل: الوظيفة + عزل المستأجر + توازن القيود؛ لا سبرنت يُغلق قبل عبورها.
9. **أي اختصار MVP يُوثَّق** بتعليق في الكود وسطر في README تحت "ديون تقنية".
10. **لا حذف لقاعدة بيانات أو volume** دون إذن صريح.
11. **الإصدارات مثبّتة** (Django 5.2 LTS تحديدًا)؛ لا تثبيت "latest" أعمى.
12. **قرار غير مذكور في هذه الوثيقة يُسأل عنه** قبل الافتراض.

| 8 | المشتريات | الدورة الثلاثية + الفاتورة المباشرة ببنود الأنواع الثلاثة + سند صرف اختياري | المسارين يولّدان نفس الحركات المحاسبية والمخزنية |
| 9 | الفوترة + ZATCA 1 | فواتير بيع (مختلطة مخزني/خدمي)، QR + XML بمعيار الهيئة | XML يجتاز مدقق الهيئة |

**نقاط تسليم قابلة للاستخدام:**
- بعد سبرنت 6: نظام محاسبي كامل لأول عميل خدمي.
- بعد سبرنت 9: نظام تجاري كامل (مخزون + مشتريات + مبيعات) بفوترة إلكترونية مرحلة 1.
- بعد سبرنت 12: ERP للمجموعات والقابضة.

**التقدير الزمني الإجمالي:** ≈ 6 أشهر بتسليم تدريجي.

- **سبرنت = prompt واحد مستقل** يُكتب بمعايير قبول واضحة، ويُشير لهذه الوثيقة.

- **Git:** commit نظيف لكل سبرنت، push إلى ريبو GitHub خاص، والنقل لسيرفر الإنتاج عبر clone + `docker-compose.prod.yml`.

## 9. إجراءات إدارية مطلوبة من الفريق (خارج الكود)

1. **فورًا:** بدء التسجيل مع ZATCA للحصول على شهادة وبيئة Sandbox.
2. **فورًا:** إنشاء ريبو GitHub خاص وربطه بالسيرفر عبر Deploy Key (لا يُشارك token في الشات).
3. **قبل الإنتاج:** تأمين سيرفر التطوير (SSH بمفاتيح فقط، fail2ban، تقييد منفذ 22 من OCI Security List) — لوحظ 3457 محاولة دخول فاشلة.
4. **قبل أول عميل:** تجهيز سيرفر إنتاج منفصل ودومين.
5. تحديد أول عميل تجريبي حقيقي لاختبار سبرنت 6.
