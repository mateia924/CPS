## 1. الرؤية ونطاق المنتج

CPS منصة SaaS متعددة المستأجرين لإدارة الأعمال، تبدأ كنظام **محاسبي ومخزني** كامل لسوق سعودي/خليجي أولًا مع بنية عالمية (لغات، عملات، أنظمة ضريبية قابلة للتوصيل).

**الفلسفة الحاكمة:** العميل الصغير (فواتير خدمية فقط) هو الأغلبية المتوقعة من العملاء، فالنظام يُصمَّم له أولًا، والقدرات الكبيرة (قابضة، شقيقة، مخزون متعدد المستودعات) "تُفتح" فوقه دون ترحيل بيانات. ERP كامل يظهر كبرنامج فواتير بسيط حتى يحتاج العميل أكثر.

**النطاق الأول المعتمد (بترتيب التنفيذ):** الهيكل التنظيمي والصلاحيات → إدارة المنصة → البيانات الرئيسية → الدليل المحاسبي → السندات → الفترات والأرصدة الافتتاحية → الأصناف والمستودعات → المشتريات → الفوترة والفوترة الإلكترونية السعودية → التقارير → التقارير المجمّعة.

**خارج النطاق الحالي (مؤجل):** الموارد البشرية الكاملة، نقاط البيع Offline، التصنيع، دورة العمل. البنية تسمح بإضافتها لاحقًا كوحدات.

## 2. حالة المشروع الحالية

ما تم إنجازه فعليًا وتم اختباره على Postgres حقيقي داخل Docker على سيرفر التطوير (Oracle Linux، مسار `/opt/cps`، منفذ 3000):

- Backend: Django 5.2 LTS + DRF + SimpleJWT، تعدد مستأجرين بعزل صريح على مستوى الصف.
- تسجيل شركة (Tenant + Owner + دليل حسابات أولي في transaction واحدة)، تسجيل دخول بـ subdomain + email + password.
- عملاء، منتجات، فواتير متعددة البنود بحساب خادمي كامل للإجماليات، وترحيل قيد متوازن عند الاعتماد.
- Frontend: Next.js + TypeScript، عربي RTL افتراضي مع تبديل للإنجليزية.
- Infra: docker-compose (postgres, redis, backend, celery_worker, frontend, nginx) بكل volumes معلّمة `:Z` لـ SELinux.
- ثغرة أمنية حرجة اكتُشفت وأُصلحت: `ModelBackend` كان يسمح بتجاوز عزل المستأجر عند الدخول. الدرس: **اختبارات عزل المستأجر إلزامية في كل سبرنت.**

**تحديث 22 سبتمبر 2026:** أُنجزت السبرنتات 0، 1، 1.5، 2، 3 — 111 اختبار آلي ناجح؛ Super Admin + 2FA؛ AuditLog محمي بـ trigger؛ Party/PartyRole؛ بنوك/صناديق/عُهد/أصول (تسجيل). ملاحظة UAT: شاشة "الأطراف" الموحدة رُفضت من منظور المحاسب → سبرنت 3.5 (3.3، 3.18).

**تحديث لاحق (نفس اليوم):** أُنجز سبرنت 3.5 (133 اختبارًا) ثم سبرنت 4
كاملًا بكتله السبع (4.0-4.7؛ 229 اختبارًا) — الدليل المحاسبي الشجري،
محرك القيود بحالة (POSTED فقط يدخل التقارير)، محرك اعتماد عام وفصل

## 3. القرارات المعمارية الجوهرية

### 3.1 الهيكل التنظيمي: شجرتان مستقلتان

**القرار:** فصل تام بين الهيكل القانوني والهيكل التحليلي. لا تُدمج "الإدارة" كمستوى في الشجرة القانونية.

| | الشجرة القانونية | شجرة مراكز التكلفة |
|---|---|---|
| المستويات | قابضة ← شركة شقيقة ← فرع (عمق غير محدود عبر parent) | إدارة / سيارة / مستودع / موظف / مشروع (عمق غير محدود) |
| طبيعته | كيان بذمة مالية ورقم ضريبي وميزانية مستقلة | تصنيف "لصالح مين" للإيراد والمصروف |
| يصدر مستندات؟ | نعم | لا |
| له ميزانية؟ | نعم | لا — قائمة دخل وكشف تفصيلي فقط |

**المبرر:** الإدارة تخدم كل الفروع ولا تنتمي لفرع واحد؛ القيد الواحد قد يتوزع على عدة إدارات؛ إعادة الهيكلة الإدارية يجب ألا تلمس البيانات القانونية أو الضريبية؛ التقرير المجمّع للقابضة يعمل على الشجرة القانونية فقط.

**الفرع والشركة يتصرفان كمراكز تكلفة تلقائيًا** في التقارير لأن كل سطر يحمل الكيان القانوني — لا يُكرَّران يدويًا كمراكز تكلفة.

### 3.2 مركز التكلفة = مركز ربحية على مستوى السطر

- شاشة مراكز التكلفة: كود، اسم، **نوع** (سيارة/مستودع/موظف/مشروع/إدارة/عام)، أب اختياري، **ربط اختياري بكيان موجود** (موظف من Master Data، مستودع من المخزون) تطبيقًا لمبدأ "التسجيل مرة واحدة"، حالة.
- **لا يوجد نوع "حساب محاسبي"** لمركز التكلفة: الحساب هو البُعد الثاني المستقل (نوع المصروف)، ومركز التكلفة هو البُعد الأول (لصالح مين). تقرير مركز التكلفة يعرض التفصيل حسب الحساب تلقائيًا.
- **قاعدة ثابتة:** حقل مركز التكلفة **على مستوى السطر** (لا المستند) في كل مستند: فواتير بيع وشراء، السندات الثلاثة، القيود اليدوية — للإيرادات والمصروفات معًا. سند صرف واحد يمكن توزيعه على عدة مراكز بعدة أسطر.

### 3.3 البيانات الرئيسية: "تسجيل مرة واحدة" في القاعدة، شاشات منفصلة في الواجهة (v1.4)

**القرار (مصحَّح في v1.4):** مبدأ "التسجيل مرة واحدة" ينطبق على **قاعدة البيانات فقط**، لا على الواجهة.

| الطبقة | القرار |
|---|---|
| قاعدة البيانات | كيان موحد `Party` + `PartyRole` (عميل / مورد / موظف / شركة شقيقة). الجهة الواحدة سجل واحد بعدة أدوار. كل Party يُربط تلقائيًا بحساب جاري في الدليل. |
| الواجهة | **شاشة مستقلة لكل كيان باسمه المألوف للمحاسب** — لا شاشة "أطراف" ولا حقل "أدوار" في أي فورم. الدور يُضاف تلقائيًا في الخلفية حسب الشاشة. |
| كشف التكرار | عند الحفظ، إذا طابق الرقم الضريبي أو الهوية/السجل طرفًا موجودًا بدور آخر → تأكيد: "هذا الطرف مسجّل كعميل — إضافته كمورد أيضًا؟" نعم = ربط الدور بنفس السجل. لا تكرار أبدًا. |
| شاشة "الأطراف" الشاملة | اختيارية تحت "إعدادات متقدمة" لمدير الحسابات فقط (`parties.view_all`) — ليست الافتراضي. |

**الشاشات المستقلة وحقول كل منها:**

| الشاشة (اسمها في القائمة) | الحقول الأساسية (ظاهرة) | الحقول المتقدمة (مطوية) |
|---|---|---|
| **العملاء** | اسم، نوع (فرد/مؤسسة)، هاتف، بريد | رقم ضريبي، سجل تجاري/هوية، عنوان، عملة، حد ائتمان، شروط سداد (أيام)، مندوب مبيعات |
| **الموردون** | اسم، نوع، هاتف، بريد | رقم ضريبي، سجل/هوية، عنوان، عملة، شروط سداد، IBAN (**حقل `Party.iban` حقيقي منذ 5.5**؛ أول إدخال حر، تغييره يمر بطلب اعتماد — 3.15.9) |
| **الموظفون** | اسم، هوية، وظيفة، هاتف | تاريخ تعيين، مدير مباشر، الفرع، عملة الراتب، مركز تكلفة مرتبط (اختياري) |
| **الشركات الشقيقة** | اسم، الكيان القانوني المقابل في الشجرة | رقم ضريبي، عملة، حساب الجاري البيني |
| **البنوك** | اسم الحساب، البنك، رقم الحساب، العملة، الكيان القانوني | IBAN (أول إدخال حر، تغييره يمر بطلب اعتماد — 3.15.9)، SWIFT، حساب الدليل، رصيد الافتتاح |
| **الصناديق** | اسم، العملة، الكيان القانوني | أمين الصندوق (موظف)، حساب الدليل، الحد الأقصى للنقدية |
| **العُهد** | اسم، الموظف (إلزامي)، العملة، الكيان القانوني | حساب الدليل، حد العهدة، تاريخ التصفية المتوقع |
| **الأصول** | كود، اسم، الفئة، تاريخ الشراء، التكلفة | العمر الإنتاجي، القيمة التخريدية، طريقة الإهلاك، الحافظ (موظف)، مركز التكلفة، الكيان القانوني |
| **المستودعات** (سبرنت 7) | اسم، الفرع، افتراضي؟ | حسابات المخزون/التكلفة/الفروق، مركز تكلفة |

كل شاشة: `DataTable` موحّد (بحث، ترتيب، صفحات، تعطيل/تفعيل، إظهار المعطّل) + فورم إضافة/تعديل + `AttachmentPanel` (3.17).

### 3.4 الدليل المحاسبي الشجري

- هرمي متعدد المستويات، عمق غير محدود، يصلح لكل الأنشطة والقابضة.
- حسابات جاري تلقائية للأطراف، وحسابات بينية للشركات الشقيقة (علامة `is_intercompany` على القيود لتمكين الاستبعاد لاحقًا).
- **قوالب دليل حسب النشاط** (خدمي مبسّط ~15 حسابًا / تجاري / صناعي / قابضة) تُطبَّق عند التسجيل بدل دليل واحد للجميع.

### 3.5 المستودعات

| الحقل | القرار |
|---|---|
| الفرع | إلزامي — المستودع تابع لكيان قانوني واحد |
| حساب المخزون / تكلفة البضاعة المباعة / فروق الجرد | ثلاثة حسابات من الدليل، تُحرَّك تلقائيًا |
| مركز تكلفة مرتبط | اختياري |
| مستودع افتراضي للفرع | نعم/لا |

**قاعدة الظهور:** نوع الصنف (مخزني/خدمي) هو ما يحدد طلب المستودع، **على مستوى السطر** لا الفاتورة: صنف مخزني → مستودع إلزامي (افتراضي الفرع تلقائيًا)؛ صنف خدمي → الحقل مخفي تمامًا ولا حركة مخزون. إذا لم يوجد إلا مستودع واحد نشط للفرع يُخفى الحقل. النتيجة: العميل الخدمي لا يرى كلمة "مستودع" أبدًا، والفاتورة المختلطة (جهاز + تركيب) تعمل صحيحًا.

### 3.6 تقييم المخزون

**متوسط مرجّح متحرك** (Moving Weighted Average) — قرار نهائي. التصميم يسمح بإضافة FIFO لاحقًا كخيار على مستوى المستأجر دون إعادة بناء.

### 3.7 المشتريات: مسارين على محرك واحد

- **الدورة الثلاثية:** طلب شراء → استلام → فاتورة مورد (للشركات ذات قسم مشتريات).
- **الفاتورة المباشرة على مرحلة واحدة:** تولّد داخليًا نفس الحركات (طلب + استلام + فاتورة) — محرك واحد لا كود مكرر.
- **أنواع البنود في فاتورة المورد:** صنف مخزني (يدخل المخزون ويُكلَّف) / خدمة / مصروف لحساب محدد (يذهب للمصروف مباشرة). لكل بند نسبة ضريبة ونوعها (قابلة للخصم / غير قابلة).
- **سند الصرف اختياري عند الحفظ:** "دفع نقدي الآن" (سند تلقائي من صندوق/بنك مختار) أو "على الحساب" (يُقيَّد على جاري المورد).

### 3.8 السندات (قبض / صرف / تسوية)

- متعددة الأسطر، كل سطر بحساب + مركز تكلفة + كيان قانوني.
- **بند مصروف بضريبة مباشرة** في سند الصرف دون الحاجة لمورد مسجّل (مثال: فاتورة بنزين) — يمنع إنشاء موردين وهميين لكل مصروف صغير.
- الربط بالبنوك والصناديق والعُهد وتوليد القيود تلقائيًا.

### 3.9 الفترات المالية المرنة

- **سنة مالية** تبدأ من أي تاريخ (ميلادي أو هجري).
- **فترات** داخلها بأي عدد وأي طول يحددها العميل.
- **ضابط غير قابل للتنازل:** الفترات داخل السنة **متتالية بلا فجوة وبلا تداخل** — يتحقق النظام تلقائيًا.
- حالة كل فترة: **مفتوحة / مقفلة / مقفلة نهائيًا** (المقفلة يفتحها مدير الحسابات؛ النهائية لا تُفتح بعد اعتماد الميزانية).
- كل مستند يتحقق أن تاريخه في فترة مفتوحة قبل الحفظ. نفس الآلية تقفل الفترة الافتتاحية.

**(بُني في سبرنت 6.1/6.7):** `FiscalYear`/`FiscalPeriod`، `assert_open_period` على كل مسار حفظ/ترحيل، التوفير التلقائي عند التسجيل + beat يومي (30 يومًا قبل النهاية)، الإقفال المتسلسل + إعادة الفتح بسبب + القفل النهائي، وقائمة إقفال الفترة الكاملة (BLOCK/WARN/INFO) بلقطة — انظر §11 القرارات 1–4، 13.

### 3.10 الأرصدة الافتتاحية

شاشات لأرصدة الحسابات والأطراف والمخزون، بشرط: **قيد الافتتاح متوازن إلزاميًا**، مخزون الافتتاح مقيَّم بالمتوسط المرجّح، أرصدة الفروع متوازنة، ثم **قفل الفترة الافتتاحية** لمنع تغير الأرقام.

**(بُني في سبرنت 6.3، للحسابات/الأطراف فقط — مخزون الافتتاح مؤجَّل لسبرنت 7):** `OpeningBalanceEntry`/`OpeningBalanceLine`، تقرير الجاهزية، الاعتماد الكتابي على مرحلتين بإقرار نصي، `JournalEntry.is_opening` (لا يُعكس، لا يُعدَّل بعد الاعتماد — التصحيح بمستند `ADJUSTMENT`) — انظر §11 القرارات 5–8، وأيضًا 3.16.3 أدناه.

### 3.11 العملات والضرائب والدول

- كل مبلغ يُخزَّن بالعملة الأصلية + سعر الصرف وقت المعاملة (قرار من الدراسة الأولى).
- تقرير العملات يشمل الأرصدة بالعملة الأجنبية و**قيد فروق إعادة التقييم** في نهاية الفترة.
- إقرار الضريبة (مخرجات − مدخلات) يُشتق مباشرة من بنود الفواتير.
- كل شركة/فرع/طرف يحمل رمز دولة → تقارير حسب الدولة كفلتر.
- **الامتثال الضريبي كحزمة قابلة للتوصيل لكل دولة** (ZATCA أولًا).

### 3.12 الفوترة الإلكترونية السعودية (ZATCA)

- **المرحلة 1:** توليد QR وXML بمعيار الهيئة — داخل سبرنت الفوترة.
- **المرحلة 2:** ربط فعلي مع بوابة الهيئة، توقيع رقمي، Clearance — تحتاج **شهادة تشفير من الهيئة وبيئة Sandbox**، وهي إجراء إداري خارج قدرة Claude Code.
- **إجراء فوري مطلوب من الإدارة:** بدء التسجيل مع ZATCA والحصول على بيئة الاختبار **بالتوازي من الآن**، لا عند الوصول للسبرنت.

### 3.13 العميل الصغير: وحدات مفعّلة ووضع مبسّط

- جدول **الوحدات المفعّلة لكل مستأجر** (Tenant Feature Flags) تتحكم به الباقة.
- **الوضع المبسّط:** إذا كانت شركة واحدة/فرع واحد، يُخفى الهيكل التنظيمي تمامًا (لا "قابضة" ولا "شقيقة")، وقائمة العميل الخدمي: عملاء — فواتير — سندات قبض — تقارير.
- المحاسبة تعمل في الخلفية دون أن يراها؛ تفعيل وحدة لاحقًا لا يتطلب ترحيل بيانات.
- **قاعدة تصميم لكل شاشة:** الحقول الأساسية ظاهرة، والمتقدم مطوي.

### 3.14 إدارة المنصة (Super Admin)

نظام منفصل تمامًا عن إدارة الشركة:

| العنصر | القرار |
|---|---|
| المستخدمون | **جدول منفصل** عن مستخدمي المستأجرين + 2FA إلزامي |
| المسار | `/platform/` أو نطاق فرعي مستقل |

### 3.15 الضوابط المالية والمحاسبية (أُضيفت في v1.1 بمراجعة مدير مالي)

هذه الفجوات اكتُشفت عند قراءة الدراسة بعين المدير المالي لا المهندس. أغلبها **يغيّر الـ Schema** ولذلك يُثبَّت قبل سبرنت 4.

#### 3.15.1 دورة اعتماد المستندات والفصل بين الواجبات
- **حالة موحّدة لكل مستند مالي** (سند، فاتورة مورد، قيد يدوي، إشعار دائن/مدين): `DRAFT → PENDING_APPROVAL → APPROVED → POSTED → (REVERSED)`.
- **القيد المحاسبي لا يُرحَّل إلا عند POSTED.** ما قبلها لا يظهر في أي تقرير مالي.
- **قواعد اعتماد قابلة للتهيئة** على مستوى المستأجر: نوع المستند + حد المبلغ (بالعملة الأساسية) → الدور المطلوب للاعتماد. مثال: سند صرف > 10,000 يحتاج دور ACCOUNTANT_MANAGER. بدون قاعدة مطابقة → اعتماد تلقائي.
- **الفصل بين الواجبات (Segregation of Duties):** منشئ المستند لا يمكنه اعتماده هو نفسه إذا وُجدت قاعدة اعتماد تنطبق عليه. المستأجر ذو المستخدم الواحد (الوضع المبسّط) يُستثنى تلقائيًا.
- كل انتقال حالة يُسجَّل في AuditLog مع الفاعل والوقت والسبب (للرفض).

#### 3.15.2 التسويات البنكية (Bank Reconciliation)
- **الحقول في Schema من سبرنت 4:** كل `JournalLine` يخص حساب بنكي يحمل `reconciled_at` (nullable) و`bank_statement_line` (FK nullable).
- **نموذج BankStatement / BankStatementLine** (بُني في سبرنت 5.5 — CSV / Excel / MT940؛ CAMT.053 مؤجَّل بانتظار ملف حقيقي من بنك، قرار معلّق P8): استيراد كشف حساب بفترة (period_start/period_end)، مطابقة تلقائية (مبلغ موقَّع + تاريخ ± يومين، مرشّح وحيد فقط) ومطابقة يدوية (بما فيها المطابقة المجمّعة N:1 بمجموع موقَّع)، وحالة `UNMATCHED` / `MATCHED` (`AUTO`/`MANUAL`) / `IGNORED`. منع استيراد مكرر (بصمة الملف) وتداخل الفترات.
- **تقرير التسوية:** رصيد البنك المعدَّل (آخر كشف + إيداعات في الطريق − مدفوعات معلّقة) ↔ رصيد الدفتر المعدَّل (الدفتر + بنود كشف لم تُقيَّد)، بعملة البنك، بنفس الشكل الذي يطلبه المدقق (`GET /api/banks/{id}/reconciliation-report/`).
- **جرد الصندوق** (`CashCount`، CFO_REVIEW_1 F14): لقطة رصيد دفتري حتى نهاية يوم العدّ، فرق يتطلب سببًا، سند تسوية اختياري عبر حساب رقابي `CASH_COUNT_VARIANCE`.
- **قفل الفترة يتحقق** أن كل الحسابات البنكية مُسوّاة حتى نهاية الفترة (تحذير، وليس منعًا — قرار المدير المالي) — سبرنت 6.

#### 3.15.3 تعدد العملات: الجانب المفقود
- **جدول أسعار صرف مركزي** `ExchangeRate` (من عملة، إلى عملة، تاريخ، سعر، مصدر: يدوي / API). كل مستند يسحب سعر تاريخه تلقائيًا ويمكن تجاوزه يدويًا مع تسجيل ذلك. (بُني في سبرنت 4؛ فرق العملة المحقق في سبرنت 5.)
- **فرق سعر الصرف المُحقَّق** عند السداد: سند قبض/صرف يسوّي فاتورة بعملة أجنبية → الفرق بين سعر الفاتورة وسعر السداد يُقيَّد تلقائيًا في حساب "أرباح/خسائر فروق العملة المحققة".
- **إعادة التقييم غير المحققة** في نهاية الفترة (كما في 3.11) تبقى، مع قيد عكسي تلقائي في أول يوم من الفترة التالية.

#### 3.15.4 الاستحقاقات والقيود الدورية
- **مستند "قيد دوري / توزيع"** `RecurringEntry`: مبلغ إجمالي، حساب مصدر (مثل "إيجار مدفوع مقدمًا")، حساب هدف (مصروف الإيجار)، فترة البداية والنهاية، عدد الأقساط → يولّد قيدًا شهريًا تلقائيًا عبر Celery في أول يوم من كل فترة.
- يغطي: المصروفات المدفوعة مقدمًا، الإيرادات المؤجلة (عقود الصيانة السنوية — وهو نفسه نموذج اشتراكات CPS)، المستحقات الدورية (رواتب مستحقة، فوائد).
- **الإهلاك** (عند تفعيله لاحقًا) يُبنى على نفس المحرك.

**(بُني في سبرنت 6.4):** `RecurringEntry`/`RecurringInstallment` بمحرك الاعتماد القياسي، `generate_due_installments` (beat يومي 01:00 UTC + عند الطلب)، فترة مقفلة → `SKIPPED` بسبب لا فشل صامت، إعادة التوليد بعد إعادة الفتح. الإهلاك يبقى مؤجَّلًا لسبرنت 6.5 (`kind=DEPRECIATION` محجوز، غير منفَّذ) — انظر §11 القرارين 9–10.

#### 3.15.5 إشعارات الدائن والمدين كمستندات مستقلة
- `CreditNote` / `DebitNote` مستندان مستقلان يشيران إلى الفاتورة الأصلية، بحساب خادمي كامل، وقيود عكسية **جزئية** (إرجاع صنفين من عشرة).
- **إلغاء الفاتورة (VOID) يبقى فقط لفاتورة لم تُرسل للعميل/الهيئة.** ما أُرسل لا يُلغى، يُصحَّح بإشعار — وهذا **شرط ZATCA** لا خيار.

**حارس VOID المؤقت (بُني في سبرنت 6.7، القرار 14):** بانتظار `CreditNote`/`DebitNote` الفعليين (سبرنت 9)، `void_invoice` يرفض (409) دائمًا لفترة إقرار ضريبي FILED/PAID، ويرفض فاتورة مُسلَّمة (`delivered_at` غير فارغ) **إلا** بصلاحية `sales.void_delivered_invoice` (Owner افتراضيًا) + سبب إلزامي — `is_post_delivery_void=True` يُعلَّم على الفاتورة وفي AuditLog. **هذا تجاوز مؤقت موثَّق صراحة، لا استثناء دائم من قاعدة الفقرة أعلاه:** الصلاحية والمسار البديل يُلغيان في سبرنت 9 حين تصبح الإشعارات الطريقة الوحيدة لتصحيح فاتورة مُرسَلة.

#### 3.15.6 الميزانية التقديرية (Budget)
- نموذج `Budget`: سنة مالية × كيان قانوني × (حساب أو مركز تكلفة) × فترة × مبلغ. إدخال يدوي أو استيراد Excel أو نسخ من فعلي السنة السابقة بنسبة.
- **تقرير الانحراف** (فعلي ↔ تقديري ↔ الفرق ونسبته) على مستوى الحساب ومركز التكلفة والكيان.
- **تنبيه اختياري** عند تجاوز نسبة محددة من الميزانية (يُعرض للمدير في لوحة التحكم).

#### 3.15.7 المرفقات على المستندات
- نموذج `Attachment` عام (GenericFK) على كل مستند مالي: صورة فاتورة المورد، إيصال، عقد. تخزين S3-متوافق، حد حجم قابل للتهيئة، وسجل من رفع ومتى.
- **تقرير "مستندات بلا مرفق"** للمدقق.

#### 3.15.8 الأصول: الإضافات والاستبعاد الجزئي (بُني في سبرنت 6.5)
- تصميم `Asset` يدعم منذ الآن: **إضافات لاحقة على الأصل** (تحسين يرفع التكلفة والعمر)، و**استبعاد جزئي** (بيع جزء من أصل مركّب)، و**نقل بين كيانات/مراكز تكلفة** مع تاريخ.
- الإهلاك (STRAIGHT_LINE ثم DECLINING_BALANCE) يُبنى على محرك القيود الدورية (3.15.4).

### 3.16 متطلبات القابلية للتدقيق والامتثال الضريبي (v1.2)

#### 3.16.1 التتبّع الكامل (Drill-down) كمبدأ في كل تقرير
- **القاعدة:** أي رقم في أي تقرير مالي قابل للنقر ينزل بالمستخدم مستوى واحدًا: قائمة الدخل → الحساب → القيود → المستند المصدر → المرفق + من أنشأ ومن اعتمد ومتى.
- **التنفيذ:** كل تقرير يُبنى على API يُرجع مع كل رقم `drill` (نوع الكيان + معرّفه + الفلاتر)؛ الفرونت يجعل كل رقم رابطًا. لا تقرير يُقبل في سبرنت 10 بدون drill-down حتى المستند.
- **الغاية:** سؤال المدقق "الرقم ده جاي منين؟" يُجاب بضغطة، لا ببحث يدوي.

#### 3.16.2 أكواد الضريبة (TaxCode) بدل النسبة العائمة
- **نموذج `TaxCode`** (من سبرنت 4 مع الدليل): كود، اسم، النسبة، النوع (`STANDARD` / `ZERO_RATED` / `EXEMPT` / `OUT_OF_SCOPE` / `REVERSE_CHARGE`)، الاتجاه (مخرجات/مدخلات)، **قابلية الخصم** (كامل / غير قابل — مثل سيارات الركوب والترفيه)، حساب الضريبة المرتبط في الدليل، رمز الدولة، وتاريخ سريان.
- **كل بند** في أي فاتورة/سند يحمل `tax_code` (FK) لا رقمًا حرًّا؛ النسبة تُسحب من الكود. **فاتورة واحدة تجمع عدة أكواد** (15% + 0% صادرات + معفى).
- **الضريبة العكسية (Reverse Charge)** على الخدمات المستوردة: تولّد قيدًا ضريبيًا مزدوجًا (مخرجات + مدخلات) تلقائيًا — أكثر نقطة تُكتشف في الفحص الضريبي.
- **الضريبة غير القابلة للخصم** تُحمَّل على حساب المصروف/الأصل لا على حساب ضريبة المدخلات.
- **فترة الإقرار الضريبي** (`TaxPeriod`: شهري/ربع سنوي حسب حجم المنشأة) **مستقلة عن الفترة المالية**، بحالة مفتوحة/مقدَّم/مدفوع، وتقرير الإقرار يُبنى عليها لا على الفترة المالية.
- قوالب أكواد ضريبية جاهزة لكل دولة ضمن حزمة الامتثال (السعودية أولًا).

#### 3.16.3 تقرير جاهزية الأرصدة الافتتاحية واعتمادها
- **قبل اعتماد الافتتاح** (سبرنت 6) يعرض النظام "تقرير الجاهزية": قيد الافتتاح غير متوازن (بالمبلغ)، أطراف بأرصدة إجمالية بدون تفصيل مستندات (Aging)، مخزون بكميات بدون تكلفة أو بتكلفة صفر، حسابات بنكية بدون رصيد كشف مطابق، حسابات في الدليل بطبيعة معكوسة (أصل برصيد دائن).
- **الاعتماد على مرحلتين:** المحاسب يُعدّ ويُقفل مؤقتًا؛ **المدير المالي (أو المالك في الوضع المبسّط) يعتمد كتابةً داخل النظام** بإقرار نصي يُحفظ في AuditLog مع الوقت والمستخدم. لا يدخل المستأجر حالة "إنتاج" قبل هذا الاعتماد.
- **قاعدة إدارية:** لا يُعامَل أي مستأجر كعميل إنتاجي بأرصدة افتتاحية غير معتمدة من محاسبه — تحمي المنصة قانونيًا.

**(بُني في سبرنت 6.3):** `GET /api/opening-balances/{id}/readiness/` بالبنود أعلاه بدرجة BLOCK/WARN/INFO، محفوظة كلقطة `readiness_snapshot` عند `submit`/`approve`؛ الاعتماد يشترط `attestation_text` ≥ 20 حرفًا + قاعدة اعتماد ثابتة `required_role=Owner` غير قابلة للحذف (D4 لا ينطبق هنا — الافتتاح يُعتمد بالمالك دائمًا، لا اعتماد اضطراري) — انظر §11 القرارين 7–8.

#### 3.16.4 اختبار القبول بمحاسب حقيقي (UAT محاسبي)
- **من سبرنت 4 فصاعدًا**، كل سبرنت محاسبي يُختبر بمحاسب بشري (ساعتان أسبوعيًا كحد أدنى) بسيناريو مكتوب: إدخال 10 قيود متنوعة، سند بعملة أجنبية، فاتورة بعدة أكواد ضريبية، ثم إخراج ميزان مراجعة وكشف حساب.
- **معيار القبول:** يجد الحساب المطلوب في ≤ 3 ثوانٍ؛ لا قيد يخرج معكوس الطبيعة؛ يفهم الشاشة بلا شرح. أي فشل = عيب في المنتج يُسجَّل كـ issue قبل إغلاق السبرنت.
- الملاحظات تُدوَّن في `docs/UAT_LOG.md` مؤرَّخة، وتُراجع في المراجعة المعمارية التالية.

### 3.17 المرفقات كدليل إثبات محاسبي (v1.3) — يحل محل التعميم في 3.15.7

**المبدأ:** زر مرفقات واحد في كل شاشة تفاصيل، لكن **سلوكه يتحدد بنوع الشاشة**:

| نوع الشاشة | معنى المرفق | القاعدة |
|---|---|---|
| مستند مالي (سند، فاتورة، قيد، إشعار، افتتاح) | دليل إثبات: إيصال، فاتورة المورد الأصلية، عقد | بعد POSTED: **إضافة فقط** — لا حذف ولا استبدال |
| بيانات رئيسية (طرف، بنك، أصل، موظف) | وثيقة هوية: سجل تجاري، شهادة ضريبية، خطاب IBAN | قابل للتحديث **مع الاحتفاظ بالنسخ القديمة** (رقم نسخة) |
| إعدادات (فترات، دليل، أكواد ضريبة) | قرار إداري: محضر اعتماد، خطاب مدقق | نادر لكن مطلوب للتدقيق |
| تقارير | لا رفع — **تصدير التقرير PDF بختم زمني** | مختلف تمامًا |

**القواعد الرقابية الست (ملزمة):**
1. **عدم القابلية للتغيير بعد الترحيل:** مرفق على مستند POSTED لا يُحذف ولا يُستبدل؛ الخطأ يُعالج برفع الصحيح وتعليم القديم "ملغى" بسبب مكتوب.
2. **بصمة الملف:** SHA-256 يُحسب عند الرفع ويُخزَّن؛ فحص دوري (Celery) يكشف أي تغيير على التخزين.
3. **سجل كامل:** الرفع والتنزيل والإلغاء تُسجَّل في AuditLog (من، متى، IP).
4. **الحد الأدنى الإلزامي القابل للتهيئة:** قاعدة على مستوى المستأجر: نوع المستند + حد المبلغ → لا اعتماد بدون مرفق من تصنيف محدد (مثال: سند صرف > 5,000 يتطلب "فاتورة أصلية"). تُدمج مع محرك الاعتماد (3.15.1). **(مُطبَّقة — بُنيت في سبرنت 6.7):** `AttachmentRule`، الفحص داخل `submit_for_approval` وفي مسار الترحيل/الإصدار المباشر حين لا قاعدة اعتماد؛ لا قاعدة افتراضية مزروعة؛ شاشة الإعدادات ← «قواعد المرفقات الإلزامية» — انظر §11 القرار 15.
5. **تصنيف المرفق:** `FATURA_ORIGINAL` / `RECEIPT` / `CONTRACT` / `BANK_LETTER` / `ID_DOCUMENT` / `APPROVAL_MINUTES` / `OTHER` — ليُبنى عليه تقرير "سندات بلا فاتورة أصلية".
6. **الاحتفاظ القانوني:** المرفقات تُحفظ مدة الاحتفاظ النظامية (السعودية: 6 سنوات للسجلات المحاسبية) حتى بعد أرشفة المستأجر؛ تدخل في سياسة الاحتفاظ بالمنصة (3.14).

**التصميم الموحّد:**
- نموذج `Attachment` (GenericFK): file, original_name, category, size, sha256, content_type, uploaded_by, uploaded_at, status (ACTIVE / VOIDED + void_reason), version (للبيانات الرئيسية), tenant.
- مكوّن فرونت `AttachmentPanel` واحد في كل شاشة تفاصيل: زر بعدّاد (📎 3)، معاينة للصور وPDF، رفع بالسحب أو **بكاميرا الجوال** (صفحة الرفع responsive)، تنزيل، إلغاء بسبب.
- **مسح فيروسات** عند الرفع (ClamAV في حاوية مستقلة)؛ الملف لا يُتاح قبل نتيجة الفحص.
- التخزين S3-متوافق بمسار `tenant_id/entity_type/year/` + **روابط تنزيل مؤقتة موقّعة** (لا روابط دائمة).
- الحدود من الباقة: حجم الملف الأقصى ومساحة التخزين الإجمالية — هنا يُطبَّق حقل `storage_mb` من سبرنت 2 فعليًا.
- **OCR (مؤجل):** الحقول جاهزة (`extracted_amount`, `extracted_date`, `extracted_ref`, nullable) لقراءة الإيصال ومقارنته بالسند وإصدار تحذير عند الاختلاف.

**التنفيذ:** سبرنت 5 (النموذج + المكوّن + Hash + AuditLog + ClamAV، مطبَّقًا على كل الشاشات الموجودة) → سبرنت 6 (قاعدة الحد الأدنى مع الاعتماد) → سبرنت 10 (تقرير المستندات بلا مرفق + تصدير PDF بختم زمني).

## 4. القواعد الثابتة الملزمة في كل سبرنت

هذه القواعد تُضمَّن حرفيًا في كل prompt لـ Claude Code:

1. **عزل المستأجر:** كل استعلام مقيّد صراحة بـ `request.user.tenant`؛ لا مسار API يقبل `tenant_id` من العميل؛ الوصول لسجل مستأجر آخر يُرجع 404 لا 403.
2. **المبالغ المالية تُحسب خادميًا فقط:** لا حقل إجمالي/ضريبة يُقبل كمدخل.
3. **الكيان القانوني على رأس المستند** (`legal_entity` إلزامي على Invoice/JournalEntry/Voucher — المستند الواحد يخص دفاتر كيان واحد؛ المعاملة البينية = مستندان في دفتري الكيانين)، و**على كل سطر:** `cost_center` (اختياري) + المبلغ بعملة المعاملة وبالعملة الأساسية مع سعر الصرف (بُني في سبرنت 4؛ عملة/سعر مستقلان لكل سطر منذ سبرنت 5).
4. **كل قيد محاسبي متوازن إلزاميًا** ولا يُحفظ غير المتوازن.
5. **كل مستند يتحقق من فترة مالية مفتوحة** قبل الحفظ (من سبرنت 6 فصاعدًا).
6. **المستودع على مستوى السطر** ويظهر فقط للأصناف المخزنية (من سبرنت 7).
7. **الحقول الأساسية ظاهرة والمتقدم مطوي** في كل شاشة.
8. **اختبارات pytest لكل سبرنت** تشمل: الوظيفة + عزل المستأجر + توازن القيود؛ لا سبرنت يُغلق قبل عبورها.
9. **أي اختصار MVP يُوثَّق** بتعليق في الكود وسطر في README تحت "ديون تقنية".
10. **لا حذف لقاعدة بيانات أو volume** دون إذن صريح.
11. **الإصدارات مثبّتة** (Django 5.2 LTS تحديدًا)؛ لا تثبيت "latest" أعمى.
12. **قرار غير مذكور في هذه الوثيقة يُسأل عنه** قبل الافتراض.
13. **لا قيد محاسبي يُرحَّل إلا من مستند بحالة POSTED** (من سبرنت 4)؛ حالة المستند موحّدة عبر النظام (3.15.1).
14. **كل شاشة تفاصيل تحمل AttachmentPanel** عبر Attachment العام؛ مرفق على مستند POSTED لا يُحذف ولا يُستبدل (3.17) (من سبرنت 5).
15. **سعر الصرف يُسحب من جدول ExchangeRate بتاريخ المستند**؛ التجاوز اليدوي يُسجَّل (من سبرنت 5).
16. **الضريبة على البند عبر `tax_code` (FK) لا نسبة حرّة** (من سبرنت 4).
17. **كل رقم في أي تقرير قابل للتتبّع (drill-down) حتى المستند والمرفق** (من سبرنت 10).
18. **كل سبرنت محاسبي يُغلق بعد اختبار قبول بمحاسب بشري** موثّق في `docs/UAT_LOG.md` (من سبرنت 4).
19. **مصطلحات الواجهة من قاموس المحاسب لا من أسماء النماذج:** شاشة مستقلة لكل كيان باسمه المألوف (العملاء، الموردون، البنوك...)، ولا يظهر للمستخدم أي مصطلح تقني داخلي (طرف، دور، كيان قانوني) إلا في الإعدادات المتقدمة (3.18).
20. **لا كود خاص بنشاط داخل أي وحدة** (`if industry == X` ممنوع) — الاختلاف بالتهيئة عبر حزمة النشاط وطبقة المصطلحات (`CPS_MASTER_PLAN.md` §2/§3، اعتُمدت 23 سبتمبر 2026).
21. **الكتالوج مصدر وحيد:** لا اسم وحدة أو نشاط أو حد خطة مكتوب يدويًا في الواجهة أو الموقع — يُقرأ من `docs/catalog/`؛ حالة الوحدة تتغير مع إغلاق سبرنتها فقط.
22. **بعد آخر commit في أي سبرنت:** `docker compose restart backend celery_worker` ثم `make smoke` على البيئة الحية قبل أي UAT أو تسليم (درس 4.8).
23. **لا محتوى تسويقي غير حقيقي:** لا شهادات أو شعارات أو عدّادات قبل وجودها؛ كل ادعاء امتثال يُكتب بحالته الفعلية؛ الوحدات غير المتاحة تُعرض «قريبًا».
