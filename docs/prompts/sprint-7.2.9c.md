**ليلة 12 أكتوبر — استنتاج لا إثبات، والترتيب يناقض صيغته البسيطة:** fail2ban أضاف قاعدته
المباشرة 14:35:18، **قبل** بدء Docker بـ16 ثانية (14:35:34)؛ فلم تكن سلاسل Docker موجودة
لتُمسح بالآلية المُثبتة. تفاعل fail2ban/direct rules مع إقلاع Docker مرجَّح لكنه **غير مُثبت**،
والسبب الدقيق لإقلاع 12 أكتوبر **مفتوح**. التفسير السابق ("firewalld يمسح السلاسل عند الإقلاع/
reload") كان هو أيضًا مُدَّعًى بلا إثبات — قاعدة 37 تنطبق على تفسيراتنا البديلة كذلك.

النتيجة حين تُمسح السلاسل: جدول nat يصبح فارغًا تمامًا: لا DOCKER ولا
MASQUERADE. النتيجة:

  (`upstream timed out while connecting to upstream ... 172.18.0.3:8000`).
- الحاويات بلا إنترنت: DNS يفشل من داخلها.

### لماذا بدا كل شيء سليمًا
- `docker ps` → كل الحاويات `Up`.
- البورتات **تسمع فعلًا**: `docker-proxy` يربطها في مساحة المستخدم، فاختبار TCP ينجح.
- الـbackend نفسه سليم: طلب مباشر إلى `172.18.0.3:8000` رد بـ400 في 0.33 ثانية.
فقط طلب HTTP حقيقي عبر nginx كشفها: `504` بعد 60 ثانية.

### الإصلاح الفوري

`live_api=200 time=0.24`، DNS يعمل، `app_https=200`، `staging=200`، `company_site=200`.

## 3. عيب في الاختبارات نفسها (نفس فئة 7.2.9-b)

`disposable_worktree` يستخدم `git worktree add --detach` الذي يسحب **HEAD**، فكانت
الاختبارات تفحص `deploy.sh` الملتزَم لا نسخة العمل: تبقى خضراء بينما الحارس مكسور في
الشجرة. أُصلح بنسخ نسخة العمل إلى الـworktree و`commit` داخله (منفصل، يُحذف عند التفكيك).

غير مُركَّب (`/app` = backend فقط، لا `/workspace`). `pytest -q` هناك يعطي دائمًا

## 7. استكمال (13 أكتوبر، بعد الحادثة)

### 7.1 `staging_refresh.sh` — الفجوة غير موجودة
الوضعان يستدعيان `backup.sh`: الكامل عند السطر 112 (`step 4.5/7`)، و`--code-only` عند
السطر 131. النسخة في الحالتين للقاعدة الحيّة (إرضاءً لحارس migrate)، لا لقاعدة staging —
وهو المقصود. البند يُشطب.

### 7.2 دور Celery worker — مُثبت: المالك
بإدخال 8000 مهمة وهمية (مستأجر غير موجود، لا كتابة) وأخذ 40 عيّنة من
`pg_stat_activity` أثناء تنفيذها، كل الاتصالات كانت:
`cps_staging | 172.20.0.9/32 | idle|active` — و`172.20.0.9` هي حاوية
`cps-staging-celery_worker-1`. الدور `cps_staging` = Superuser + BYPASSRLS.

**كل مهمة Celery تعمل خارج عزل المستأجرين.** ليس تسريبًا بذاته (المهام كود داخلي، لا
استعلامات يوجّهها مستخدم)، لكنه يعني أن RLS لا تحمي السطح غير المتزامن إطلاقًا: أي مهمة
تنسى فلتر المستأجر تقرأ وتكتب عبر المستأجرين بصمت، ولا اختبار يمسكها (الاختبارات نفسها
بالمالك). ويفسّر ما رأيناه في 7.2.9-b: `/password-reset/request/` نجح دائمًا (الـworker
مالك) بينما `confirm` فشل (gunicorn مقيَّد).

**لا إصلاح الآن — القرار تصميمي:** المهام العاملة داخل مستأجر واحد تضبط السياق وتعمل
بالدور المقيَّد؛ والمهام العابرة للمستأجرين بطبيعتها (ملخّص يمرّ على الكل) تبقى بالمالك
باعتماد مكتوب. سبرنت مستقل.

### 7.3 اختبارات حارس النشر: تخطٍّ معلن بدل خطأ كاذب
`pytestmark = skipif(...)` حين لا يتوفر جذر الريبو أو git. dev الآن: `4 skipped` بدل
`4 errors`. ولئلا يتحول التخطي إلى "لا تعمل في أي مكان"، أُضيفت خطوة في `ci_local.sh`
تشغّل الملف وحده وتتحقق أن الناتج يحتوي `4 passed` — لا مجرد خروج بصفر.

### 7.4 قفل pytest
`scripts/pytest_run.sh` يحمل `flock -n /run/cps-pytest.lock`؛ التشغيل الثاني يُرفض
برسالة صريحة وخروج 1 بدل أن يشارك قاعدة الاختبار. `ci_local.sh` يمرّ عبره الآن.
**الإثبات:** مع احتجاز القفل، التشغيل الثاني يطبع `REFUSED` ويخرج 1؛ وبعد تحرره يعمل عاديًا.
وسابقًا: تشغيلتان متوازيتان حقيقيتان — الأولى `16 passed`، الثانية `exit=1` بلا أي ناتج.
الأمر اليدوي الموثَّق صار: `scripts/pytest_run.sh cps-dev-backend-1 -q [args]`.

### 7.5 ما تبقّى
- **UptimeRobot** (مراقبة خارجية) — لم يُنفَّذ بعد. أولوية أولى.
- سؤال الاستضافة عن الـreboot (إطفاء ACPI 13:55:55 يوم 12 أكتوبر) — التذكرة جاهزة. مصدر
  `0:65535` **مُجاب محليًا** (fail2ban recidive، §1) فلا يُسأل عنه.
- تأمين SSH (526 محاولة/يوم) — fail2ban **كان مثبَّتًا أصلًا** (خلافًا لما قالته البنود)؛ يبقى
  المفتاح بدل كلمة السر و`PermitRootLogin`. وjail `recidive` لم يحظر أحدًا قط حتى 13 أكتوبر (§7.7).
- دور Celery (أعلاه) — سبرنت مستقل.
- نشر live لـ7.2.9 + 7.2.9-b — مؤجَّل عمدًا حتى تكتمل المرحلة ب (SMTP).

### 7.6 خلل في حارس 7.2.9-c نفسه (اكتُشف 2026-10-13 أثناء 7.3)
**الأثر:** 166 إعادة تشغيل غير ضرورية لـDocker بين 15:40:01 و21:10:01 (كل دقيقتين بلا انقطاع)،
كل واحدة تُسقط live وstaging وdev معًا. توقّف الـdaemon نفسه 17.3–33.6 ثانية (متوسط 26.8،
مجموع ≈74 دقيقة) من journalctl، تُضاف إليها مدة إقلاع الحاويات (≈30–50 ثانية لكل دورة حتى يعود
live للاستجابة). سجل الحارس: 166 سطر `MISSING — restarting docker` يتبع كلًّا منها
`STILL MISSING after restart` — بينما السلسلة كانت موجودة طوال الوقت.

**السبب المباشر:** ملفات `/etc/cron.d` لا ترث PATH من `/etc/crontab`؛ PATH الافتراضي
`/usr/bin:/bin` لا يحوي `/usr/sbin/iptables` → خروج 127 في كل فحص.
**السبب الجذري:** حارس لا يميّز "تعذّر الفحص" من "وُجد عطل" — أي خروج غير صفري كان يُقرأ
"السلسلة مفقودة"، وبلا حدّ لعدد مرات الإعادة، ولا توقف بعد فشل الإعادة.

**الإصلاح (`scripts/docker_firewall_guard.sh` + `infra/cron/cps-docker-firewall-guard`):**
- iptables بالمسار المطلق، وPATH صريح في السكربت وفي سطر cron.
- ثلاث نتائج للفحص لا اثنتان: موجودة → خروج 0؛ غائبة فعلًا (خروج 1 **و** نص
  `No chain/target/match by that name`) → إعادة تشغيل؛ أي شيء آخر (ثنائي غير موجود/غير
  قابل للتنفيذ، قفل xtables، خطأ آخر) → سطر `cannot check` وخروج 0 بلا إعادة.
- حدّ: إعادة واحدة كحد أقصى كل 30 دقيقة (`/var/lib/cps-docker-firewall-guard/last_restart`).
- إن بقيت غائبة بعد الإعادة: `STILL MISSING — manual intervention needed` ويتوقف الحارس
  نهائيًا (`gave_up`) حتى يُحذف الملف يدويًا.

**الإثبات (21:11–21:12):** PATH مجرَّد إلى `/bin:/usr/bin` → خروج 0 بلا إعادة (المسار المطلق
يجعل الفحص ينجح فعليًا، فلا يُكتب `cannot check` في هذه الحالة)؛ `IPTABLES=/nonexistent` →
`cannot check` وخروج 0؛ iptables مزيَّف بخروج 4 (قفل xtables) → `cannot check`؛ سلسلة غائبة
مع إعادة قبل <30 دقيقة → `not restarting again`؛ مع `gave_up` → لا إعادة. MainPID لـdockerd
ثابت قبل كل ذلك وبعده. **غير مُختبَر:** فرع "غائبة فعلًا والحارس مسلَّح → إعادة حقيقية" —
اختباره يعني إعادة تشغيل Docker فعلًا.

### 7.7 انقطاع 2026-10-13 23:43–23:47 (سبّبه تغيير مُعتمَد من المالك)
**السبب:** تغيير إعداد fail2ban اعتمده المالك وطُبِّق 23:43 على خادم إنتاج، في اليوم نفسه الذي
شُخِّص فيه انقطاع الـ25 ساعة من النظام الفرعي نفسه. التغيير: `banaction_allports =
firewallcmd-ipset[actiontype=<allports>]` في `jail.local` لإصلاح jail `recidive` (§1).
**المدة:** ~4 دقائق (live_https لا يردّ من 23:43:36 حتى عودة Docker بعد 23:46:58).

**التسلسل المرصود (مباشرة، لا استنتاجًا):**
```
23:43:14  iptables -t nat -L DOCKER  → Chain DOCKER (2 references)        (سليمة)
23:43:36  systemctl restart fail2ban → بدء نظيف، recidive=firewallcmd-ipset، 10 IPs في f2b-recidive
23:43:5x  iptables -t nat -L DOCKER  → "iptables: Incompatible with this kernel."
          nft list table ip nat      → السلاسل الأربع الافتراضية فقط — لا DOCKER ولا قواعده
          curl -k https://localhost/ → 000 (مهلة 10 ث)؛ http → 200؛ docker ps → كله Up
23:44:01  الحارس: "cannot check ... Incompatible with this kernel — NOT restarting docker"
23:46:01  الحارس: نفس السطر
23:46:33  systemctl restart docker (يدويًا من المالك) → 23:46:58 Started
23:49     Chain DOCKER (2 references)؛ live https: 200
```
لا reload لـfirewalld في الـjournal في تلك النافذة؛ الحدث الوحيد إعادة تشغيل fail2ban.
هذا هو إثبات الآلية في §1.

**لماذا لم يُصلح الحارس نفسه:** بعد المسح لا ترجع `iptables` (خلفية nft) "No chain/target/match
by that name" بل "Incompatible with this kernel"، فيصنّفها الحارس "تعذّر الفحص". **الحارس أعمى
عن هذا النمط من العطل، لا مجرد متحفّظ** — كان سيترك live ساقطًا بلا حدّ.

**ما زال قائمًا:** إعداد fail2ban الجديد مثبَّت ويعمل (recidive يحظر فعلًا: قاعدة direct واحدة
`-m set --match-set f2b-recidive src -j REJECT` على كل المنافذ)، **غير ملتزَم**
(`infra/fail2ban/jail.local` في الشجرة فقط). النسخة الأصلية محفوظة خارج الريبو.

### 7.8 قرارات مفتوحة للغد (لا تنفيذ الليلة)
1. **جعل Docker صامدًا أمام إعادة كتابة firewalld:** منطقة firewalld خاصة به، أو إخراج شبكة
   الحاويات من يد firewalld كليًا. هذا هو الإصلاح الجذري؛ ما بعده تخفيف.
2. **إعادة تسليح الحارس:** يقرأ الخلفية الحقيقية (`nft list table ip nat` لا `iptables` فقط)،
   ويشترط إشارة ثانية (live لا يردّ عبر HTTP حقيقي، قاعدة 36) قبل أي إعادة تشغيل.
3. **إعداد fail2ban:** إبقاؤه (يعمل، ويُلتزَم) أو إرجاعه. أيّ إعادة تشغيل لـfail2ban — بما فيها
   الإرجاع — تمسح السلاسل حتى يُحسم البند 1؛ تُنفَّذ فقط مع إعادة تشغيل Docker مُخطَّطة بعدها.
4. سبب انقطاع 12 أكتوبر بالضبط (§1) — مفتوح.
